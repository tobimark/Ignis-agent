## 0. 一句话

Ignis v0.1 是一个用 Rust 从零实现执行循环、可切换内核（native / codex / claude）、具备长期记忆、技能与后台定时任务的个人 AI Agent，交付为可在干净 Ubuntu 环境安装、运行、验证的完整仓库。

## 1. 意图与为什么

作者（唯一用户与维护者）要把它作为**能力证明**展示给目前就职的公司：证明自己能够独立完成一个「可托付真实任务的个人 AI Agent」，不是聊天玩具，也不是套壳。

因此所有取舍按以下优先级裁决：

1. **真** — 真实执行任务（跑测试、改代码、查系统），不是模拟结果；
2. **稳** — 干净环境装得上，常见任务跑得通、不报错、不崩；
3. **讲得清** — 分层清晰，作者能解释每一层的设计与取舍；
4. 功能是否更多 —— 排最后。

隐含观众是公司同事：README、架构说明与演示材料要能让外人独立看懂并跑起来。

对外一句话叙事（demo.md）：*Ignis should remember, act, and improve.*

## 2. 目标 / 非目标 / 反目标

### 2.1 目标（v0.1 必须做到）

按 demo.md 六大模块，含对话后的修改：

1. **CLI**：`ignis` 交互式 REPL；流式输出；工具执行可见（`→ Reading package.json` 形式）；审批（Approve / Reject / Details）；Ctrl-C 主动中止。
2. **Agent Core（native 内核，从零实现）**：多轮任务循环、流式事件、工具调用、基于结果的继续推理、失败重试、步数/时间/成本上限。
3. **Runtime 适配器**：统一接口 + 三个实现——`native`（主路径，完整工具与审批）、`codex`、`claude`（兼容内核）。可运行时切换。
4. **工具系统**：文件、Shell、网络（HTTP）三类工具 + 权限控制。
5. **Memory**：跨会话持久化；任务前检索注入；CLI 查看 / 修改 / 删除；纠正后旧信息不再生效；重启后仍然生效。
6. **Skills**：兼容 SKILL.md 目录约定；扫描、选择、加载、执行；返回实际使用的 Skill 名称；内置 2–3 个开箱技能。
7. **Scheduler**：间隔任务 + 常用 Cron；后台守护进程在 CLI 退出后继续运行；创建 / 暂停 / 恢复 / 查看执行历史；失败有记录、不无限重试；不绕过权限限制；每任务有超时与资源上限。
8. **执行日志与成本**：结构化任务日志；任务结果、失败原因可查看；token 记账与调用成本上限。
9. **三个演示场景（P0）**：A 修测试失败、B 跨会话记忆、C 后台主动工作（详见 §7）。
10. **交付物**：可安装的 ignis 单二进制 CLI；README（干净 Ubuntu 可按文档安装启动）；覆盖三个场景的端到端测试；Docker / systemd 部署示例。（demo.md 中的「Telegram Bot 接入示例」随 IM 推迟。）

### 2.2 非目标（明确不做）

demo.md 推迟清单照单全收：多 Agent 协作、Web Dashboard、语音交互、自动生成 Skills、多模型路由/负载均衡、向量数据库与知识图谱、多用户/SaaS、Skill 商店。

对话新增的推迟项：

- **Telegram 等 IM 对接**：v0.1 不做；通知通道留接口，后续可插入（见 §6.7）。
- **跨内核实统一 MCP 工具层**：v0.1 不做；接口留口子（见 §6.3）。
- 真正的自主学习：只做「保存并复用成功经验」。

### 2.3 反目标（作者原话，出现即视为失败）

- 程序安装不上；
- 装上了，随便运行个什么任务就报错；
- 演示中途崩溃，或被人一句「这不就是套壳」问倒；
- 安全越界：超出工作区、风险操作不经审批、token / key 进入日志。

## 5. 系统总览

```
                 ┌───────────────────────────────────────────────┐
  用户 ──────▶   │ apps/cli（bin: ignis）                        │
                 │  REPL · 子命令 · 审批 UI · daemon 模式入口     │
                 └───────────────┬───────────────────────────────┘
                                 │ Session / Task
                 ┌───────────────▼───────────────────────────────┐
  daemon 模式 ──▶ │ packages/core（ignis-core）                    │
                 │  tasks · sessions · memory · skills            │
                 │  scheduler · security（审批/策略）              │
                 └──────┬───────────────────────┬────────────────┘
                        │ Runtime trait          │ Storage
                 ┌──────▼────────────┐   ┌───────▼──────────┐
                 │ packages/runtime  │   │ packages/storage │
                 │ native / codex    │   │ rusqlite(bundled)│
                 │ / claude          │   │ ~/.ignis/        │
                 └───────────────────┘   └──────────────────┘
                 ┌───────────────────┐
                 │ packages/gateway  │  守护进程逻辑：调度循环、通知投递
                 │  Notifier（IM 预留）│  （由 cli 的 daemon 模式驱动）
                 └───────────────────┘
```

- **Ignis Core 拥有**：长期状态（会话、任务、记忆、技能、调度）、权限、日志——与用哪个内核无关。
- **Runtime 负责**：一次任务的推理与执行循环，向 Core 输出统一事件流。
- **依赖方向**：core → runtime（runtime 定义 `ToolExecutor` 等 trait，core 实现并注入）；见 §4#16、§6.3。
- **数据流**：CLI 或 Scheduler 发起 Task → Core 组装上下文（记忆、技能、工作区）→ Runtime 执行（工具调用经 security 层审批）→ 事件流回写日志与 UI → 任务结束写记忆候选与成本记账。
- **后台路径与前台路径共用同一套 Runtime / 工具 / 审批策略**，区别仅在权限 profile（见 §6.4）。

## 6. 模块设计

### 6.1 CLI（apps/cli）

命令面（clap v4）：

```
ignis                      # 交互式 REPL（默认）
ignis run "<task>"         # 一次性任务
ignis daemon start|stop|status
ignis schedule list|pause|resume|remove|history
ignis alerts [--all] [--read]
ignis memory list|search|add|edit|delete
ignis skills list
ignis task show <id>       # 任务详情与执行日志
ignis config show|set
ignis doctor               # 环境自检（配置、模型连通性、目录权限、外部内核探测）
```

全局参数：`--kernel native|codex|claude`（默认取配置）、`--workspace <dir>`、`--yes` / `--unsafe`（非交互预授权，见 §6.4）。

REPL 体验要点：

- 任务开始/结束的清晰分隔；工具执行以 `→ <动作>` 单行展示；流式文本增量输出。
- 审批以内联提示：`[a]pprove / [r]eject / [d]etails`；可选择「本会话内同类操作总是允许」。
- Ctrl-C：第一次中断当前任务（经 Runtime 中止 + 工具进程终止），空闲时退出。
- 启动时若有未读告警，顶部横幅提示，`ignis alerts` 查看。
- 错误对人话：预期错误（模型 401、工作区越权、命令被拒）不打印堆栈。
- `doctor` 在选中外部内核时，检查对应 CLI 是否存在及其版本。
- 非交互模式（无 TTY，如管道调用、e2e、Docker 冒烟）的审批行为见 §6.4。

### 6.2 Agent Core 与 native 内核（packages/core + runtime/native）

一次任务（Task）的生命周期：

1. **上下文组装**：系统提示（人格、工作区信息、工具说明、技能目录）+ 记忆注入（§6.5 检索结果）+ 历史消息。
2. **循环**：向模型发起流式请求 → 增量文本出事件 → 解析工具调用 → 经 security 层审批并执行 → 工具结果回填 → 继续，直至模型给出最终答复或触碰上限。
3. **上限**：最大步数、任务墙钟超时、token/成本上限（native 从 API usage 精确记账；见 §6.3、§6.8）。
4. **中止**：tokio `CancellationToken` 贯穿模型请求与工具进程；外部进程按进程组终止（Unix）。
5. **重试**：仅对瞬时错误（网络、5xx、速率限制）做有限退避重试；工具失败作为结果回填给模型，由模型决定下一步，不自动重放危险操作。
6. **上下文管理（v0.1 从简）**：system + 记忆固定保留，历史超预算时裁剪最老消息；不做自动摘要。

实现要点：tokio 异步；HTTP 用 reqwest（rustls-tls，避免 OpenSSL 系统依赖）；SSE 手写解析或轻量 crate；工具调用协议为 OpenAI 兼容 `tools` / `tool_calls` 流式分片组装。

### 6.3 Runtime 接口与三个内核（packages/runtime）

统一接口（Rust 示意，具体签名由构建者定）：

```rust
pub trait Runtime: Send + Sync {
    fn id(&self) -> &'static str;                     // "native" | "codex" | "claude"
    fn capabilities(&self) -> Capabilities;           // tools / approvals / usage
    fn run(&self, req: RunRequest, ctrl: CancellationToken)
        -> BoxStream<'static, RuntimeEvent>;          // async-trait / BoxFuture 均可
}

pub enum RuntimeEvent {
    TextDelta   { text: String },
    ToolExec    { name: String, args: serde_json::Value }, // 外置内核：只观察
    ToolResult  { ok: bool, output: Option<String> },
    ApprovalRequest { /* native 专用 */ },
    Usage       { input_tokens: u64, output_tokens: u64 },
    Done        { status: RunStatus, summary: Option<String> },
}
```

- **依赖方向（决策 #16）**：runtime 定义 `ToolExecutor` / 事件通道等 trait；core 实现（含审批与记录）并随 `RunRequest` 注入给 native 循环。因此 crate 图是 core → runtime，无循环依赖；native 循环自身可脱离 core 用假 executor 单测。
- **native**：唯一完整实现——自有工具、审批、用量记账、中止。
- **codex**：`codex exec --json -C <workspace> --sandbox workspace-write --skip-git-repo-check <prompt>`，解析 JSONL 事件映射为 RuntimeEvent。审批=启动参数给定的沙箱策略（非交互模式无法弹审批）；工作区外访问由沙箱天然阻止。
- **claude**：`claude -p --output-format stream-json`（cwd=工作区），映射事件；权限由 CLI 自身的 permission-mode / allowed-tools 参数限定在安全基线内。
- **能力边界**（决策 #4）：记忆读=prompt 注入，三内核一致；记忆写（`remember`）与技能全文加载（`load_skill`）完整能力仅 native；外置内核获得技能目录列表（可自行读取 SKILL.md，尽力而为）。
- 两个外部内核的用量可能缺失 → 成本上限对它们退化为「墙钟 + 步数」；文档与 CLI 要明说这一限制。
- **约束**：外置内核不做 Ignis 工具注入（浅兼容）；接口预留统一 MCP 工具层的扩展位，后续可用 MCP 把 Ignis 工具共享给它们而不改上层。

### 6.4 工具与安全（packages/core/security + tools）

工具最小集（三类 + 元工具）：

- **文件**：`fs_read`、`fs_list`、`fs_write`、`fs_edit` —— 路径解析后必须落在工作区内。
- **Shell**：`shell_run` —— 指定工作目录，超时、输出截断上限；危险命令模式库（`rm -rf`、`sudo`、`curl|sh`、`chmod 777` 等）强制审批。
- **网络**：`http_fetch` —— 对外请求需审批（或域名白名单）；响应大小上限。
- **元工具**：`remember`（写记忆）、`load_skill`（加载技能指令）、`schedule_create`（自然语言建调度任务）、`notify_user`（告警/通知：severity + 标题 + 正文）。

审批策略：

- 默认策略：写操作、Shell、对外请求 = 询问；读取 = 允许；敏感文件（`.env`、密钥、`~/.ssh` 等）读取 = 询问。
- 「本会话总是允许」的批准记入会话级规则；跨会话持久规则 v0.1 不做（避免放权失控）。
- **非交互 / 无人值守**（决策 #15）：无 TTY 且未加开关时 fail-closed——写/Shell/外联动作一律拒绝并记录原因，模型收到拒绝结果并可继续；`--yes` 预授权常规风险动作；危险命令库需显式 `--unsafe` 才放行。所有预授权同样写审批记录（审计不缺席），e2e 与 harness 均以 `--yes` 驱动。
- **后台任务**（决策 #18）：创建时即确定权限 profile（允许的工具集 + 风险上限 + 工作区 + 时间/token 上限），运行期间严格执行；超出 profile 的动作直接失败并记录，不排队弹窗；失败与原因进入执行历史与通知。**v0.1 调度任务仅允许 native 内核**（外置内核无法逐动作执行 profile），创建时校验并提示。
- 每个工具调用与审批决定写结构化日志（§6.8）。

### 6.5 Memory（packages/core/memory）

两类记忆（demo.md）：

- **用户记忆**：长期偏好、环境信息、项目背景（如「这个项目使用 uv 管理 Python 环境」）。
- **任务经验**：成功执行过的步骤、常见错误（如「构建前要装某依赖」）。

存储：`~/.ignis/ignis.db`（rusqlite，bundled 内嵌 SQLite，含 FTS5）；**中文检索使用 FTS5 trigram 分词器**（对中文子串匹配友好；SQLite ≥ 3.34 支持，bundled 版本满足——开工 spike 验证）；Markdown 镜像（`~/.ignis/memory/*.md`）由数据生成，供人直接阅读。

事实模型（草稿）：

```
facts(id, scope[user|project|global], key, text, status[active|superseded],
      superseded_by, source_task_id, created_at, updated_at)
```

- **纠正规则**：同一 `key` 写入新值即把旧值标 `superseded`；检索只取 `active`。这直接支撑 Demo B「纠正后不再用旧信息」。
- **项目作用域**：`scope=project` 关联具体工作区路径。

检索与注入（决策 #21）：当前工作区的 active `project` 事实**无条件注入**（受上下文预算约束），不依赖关键词命中——保证 Demo B 一类场景稳定；FTS 检索用于 user/global 事实与任务经验，按相关度 + 新近度取前 N 条，注入系统提示的「已知信息」段。任务结束允许模型调用 `remember` 沉淀新知识/经验。

CLI：`memory list/search/add/edit/delete`；编辑与删除同时清理镜像文件。

### 6.6 Skills（packages/core/skills）

- 来源：仓库内置 `skills/`（**构建时嵌入二进制**，include_dir / rust-embed 选型留给构建者）+ 用户目录 `~/.ignis/skills/`；两者合并扫描，展示来源。无需从仓库目录运行；Docker 只需二进制。
- 格式：每个技能为 `SKILL.md`（YAML frontmatter：`name`、`description`；正文为指令，可带 `scripts/` 等资源）。
- 流程：启动扫描 → 名称 + 描述注入系统提示（渐进披露）→ 模型调用 `load_skill` 读取全文 → 按指令用工具执行 → 任务日志记录实际使用的技能名，CLI 展示。
- 内置三个技能（与演示对应）：
  - `project-analyzer`：项目结构/测试失败分析的步骤手册；
  - `server-health`：磁盘、内存、Docker 状态的检查步骤；
  - `report-generator`：把结果整理成 Markdown 报告。

### 6.7 Scheduler、Gateway 与通知（packages/core/scheduler + packages/gateway）

- **守护进程**：`ignis daemon start` 默认自守护（fork 后台、写 pidfile、单实例 flock、日志重定向到 `~/.ignis/logs/`）；`--foreground` 供 systemd / Docker 使用。启动时加载 active 任务 → 按间隔/Cron 计时 → 到期以受限 profile 发起 Task（走与前台相同的 Runtime / 工具 / 审批执行路径，v0.1 仅 native）→ 写执行记录 → 投递通知。
- 在 CLI 中创建第一个调度任务时，若检测到 daemon 未运行，提示并可直接拉起（一次确认）。
- **任务模型**：`jobs(id, name, prompt, schedule_kind[interval|cron], schedule_expr, kernel, profile_json, limits_json, status[active|paused], created_at)`；`job_runs(id, job_id, started_at, ended_at, status, summary, error, usage)`。
- **失败策略**：失败即记录 + 通知，不无限重试（默认零重试）；重叠执行跳过；停机错过的执行不补跑（防重启后重复执行危险操作）。
- **通知通道**：`Notifier` 接口；v0.1 渠道 = ① CLI 未读收件箱（`ignis alerts`）② 桌面通知（`notify-send`，本机可用）③ 日志文件。Telegram 等 IM 作为一个新 Notifier 后续插入（packages/gateway 是预留接入点）。
- **告警来源与去重**（决策 #19）：任务失败必通知；模型可在任务中调用 `notify_user` 做条件告警（Demo C 的「超过 85% 就通知我」）。同一 job + 标题在冷却窗口（默认 15 分钟）内去重，避免刷屏。`alerts` 表含 severity、未读状态、来源任务/运行 id。
- 任务创建：用户在 CLI 里说「每隔 10 分钟检查…」→ 模型调用 `schedule_create` → 展示确认（含 profile 与上限）→ 落库。

### 6.8 存储、配置与日志（packages/storage）

- `~/.ignis/`：`config.json`、`ignis.db`、`logs/`、`memory/`、`skills/`。
- 配置（env 可覆盖）：工作区根、默认内核、模型协议/baseUrl/model/apiKeyEnv、审批策略、上限（任务超时、最大步数、token/成本）、可选价格表。
- **密钥规则**：key 只从环境变量或 `config.json`（0600）读取；日志与错误输出统一脱敏；审计确认 key 不进入任何日志文件。
- 日志：任务级结构化 JSONL（事件流 + 工具调用 + 审批决定 + 用量），SQLite 存索引与聚合，供 `ignis task show` 与调度历史查询。
- **记账与上限**（决策 #20）：默认按 token 上限（native 从 API usage 精确计数）；USD 上限需在配置提供价格表（每模型 in/out 每百万 token 单价），未配置价格表或遇到未知模型时降级为 token 上限并在 UI 提示；外部内核降级为时间/步数上限。

### 6.9 部署

- **安装（README 主线）**：干净 Ubuntu → 安装构建依赖（gcc/cc）+ rustup → 克隆仓库 → `cargo build --release`（或 `cargo install --path apps/cli`）→ `ignis doctor` → `ignis` 即用。产出单二进制，无运行时依赖（glibc 基线）。
- **Docker**：多阶段构建（rust 构建镜像 → slim 运行镜像，只带二进制——内置技能已嵌入），数据卷挂载 `~/.ignis`；可选 musl 静态构建提升可移植性。
- **systemd**：`ignis-daemon.service` 示例单元文件，ExecStart 为 `ignis daemon start --foreground`（日志走 journald）。

## 7. 三个演示场景的落地（P0）

每个场景提供**仓库内夹具 + 端到端测试**，保证演示可重复。（夹具项目语言与 Ignis 无关——Demo A 刻意用一个 Node 小项目，顺带展示语言无关性。）

### Demo A · AI 真正完成工作

- 夹具：`examples/broken-project/`（一个含失败测试的项目：配置路径假设错误导致测试失败；`npm test` 可复现）。
- 流程：`ignis run "分析这个项目的测试失败原因，修复它并重新运行测试"` → 读文件 → 跑测试 → 定位 → 请求写权限 → 修改 → 重跑 → 汇报。
- 端到端断言：测试从失败变通过；产生写操作审批记录；任务日志完整。

### Demo B · AI 记住过去的经验

- 夹具：`examples/uv-project/`（`pyproject.toml` + 测试；依赖管理走 uv）。
- 流程：会话 1 用户说「这个项目使用 uv 管理 Python 环境」→ `remember(scope=project, key=pkg_manager, uv)`；**退出重启**；会话 2「帮我检查这个项目的依赖并运行测试」→ 检索注入（project 事实无条件注入，见 §6.5）→ 使用 `uv sync` / `uv run` 工作流，而非 pip。
- 断言：重启（新进程）后记忆可检索；工具日志中出现 uv 工作流命令；纠正场景（改说 pip）后旧事实 `superseded` 不再注入。
- 备注：真实演示需安装 uv（README 注明）；自动化测试断言「选择了 uv 工作流」而不依赖真实依赖安装。

### Demo C · AI 在后台主动工作

- 夹具：`examples/test-server/check-health.sh [--simulate <diskPct>]` → 输出磁盘/内存/Docker 状态 JSON。
- 流程：用户说「每隔 N 分钟检查测试服务器，磁盘超过 85% 就通知我」（演示用 N=1）→ `schedule_create`（native，profile 含 `notify_user`）→ **退出 CLI** → 守护进程继续 → `--simulate 92` 触发 → 模型调用 `notify_user` → 告警落库 + 通知渠道投递 + 执行历史可见。
- 断言：CLI 退出后任务仍触发；告警存在且可见（`ignis alerts`）；执行记录含成功/失败状态；进程重启不重复执行。

## 8. 测试策略

- **单元**：security（路径逃逸、危险命令判定、审批决策、非交互 fail-closed）、memory（supersede、检索、中文 trigram、project 无条件注入）、scheduler（cron/间隔、重叠跳过）、事件映射。
- **集成**：Runtime 三个适配器——native 打本地假模型服务（HTTP fixture）；codex/claude 用可执行假 CLI（shell 脚本产出固定 JSONL / stream-json）验证映射与错误处理；不依赖真实模型跑 CI。
- **端到端**：§7 三场景，用 assert_cmd 驱动真实构建出的 `ignis` 二进制 + 短周期调度 + 假通知通道注入；无人值守场景用 `--yes` 运行，并断言审批记录仍然写入。
- **安装冒烟**：Docker 容器内构建 + `ignis doctor` + 一次离线冒烟任务（不触网、不调模型）。
- 运行方式：`cargo test`（workspace 全量）。

## 9. 留给构建者的部分

- crate 选型细节：rustyline vs reedline；cron vs croner；chrono vs time；async-trait vs 手写 BoxFuture/BoxStream；daemonize crate vs 手写 double-fork；notify-rust vs 直接 spawn `notify-send`；include_dir vs rust-embed（内置技能嵌入）；配置格式 JSON vs TOML。
- 数据库 schema 字段级细化与迁移机制（手写 SQL migrations 起步）；提示词文案与上下文预算细节。
- OpenAI 兼容流式工具调用的实现细节（SSE 解析、分片组装、错误形态兼容）。
- clap 子命令结构与参数命名细节、REPL 渲染细节（颜色、截断、进度提示）。
- 重试次数、退避参数、token 预算默认值、输出截断阈值等可调参数的默认值。
- 夹具项目的具体内容（broken-project 的 bug 形态、uv-project 的测试、check-health.sh 的字段）。
- README 结构与演示脚本写法；Dockerfile / systemd 单元文件细节；musl 静态构建是否启用。
- codex / claude 适配器的具体参数（沙箱/权限开关在目标版本上的确切用法，开工时按已装版本实测）。

## 10. 风险与开工即验证项

1. **中转的流式工具调用兼容性**（native 内核命门）：开工第一步 spike——用现有中转 key 打一轮「流式 + 工具调用」的最小请求；不通则退到非流式或换协议实现。
2. **Rust 环境就绪**：`rustup default stable` 一步启用（工具链已装）；crates.io 可达性已验证（评审实测 200），镜像（rsproxy / USTC）仅作备用。
3. **rusqlite bundled 的 FTS5 / trigram**：bundled 构建默认带 FTS5，trigram 需 SQLite ≥ 3.34；与第 1 项同批 spike 验证（插入中文、trigram MATCH 查询）。
4. **外部 CLI 事件格式漂移**：锁定已测版本（codex-cli 0.162.1、Claude Code 2.1.274），适配器对未知事件宽容跳过；版本探测写入 `ignis doctor`。
5. **uv 未安装**：Demo B 真实演示依赖 uv；README 给出安装方式，自动化测试不依赖。
6. **成本上限在外置内核上不精确**：以时间/步数兜底，UI 与文档明示。
